# 개발 협업 방식 (에이전트 ↔ 개발자)

> 상태: v1 · 최종 수정: 2026-08-17
> 이 문서는 "내가 직접 개발하되, 에이전트를 어떻게 쓸 것인가"를 정한 규칙이다.
> 목표: **공부하면서 개발한다.** 속도보다 이해가 우선이다.

---

## 0. 한 줄 원칙

- **프론트엔드** — 경험 있음 → 에이전트가 초안을 만들고, **내가 리팩토링**하며 이해한다. (반반)
- **백엔드** — 경험 없음 → 에이전트는 **요구사항과 가이드만** 주고, **내가 직접 구현**한다. (내가 100%)

핵심: 에이전트는 절대 백엔드 코드를 대신 완성하지 않는다. 프론트엔드는 "완성 초안"을, 백엔드는 "지도(map)"를 준다.

---

## 1. 개발 단위 = 수직 슬라이스 (Vertical Slice)

기능을 프론트 전체 → 백엔드 전체 순서로 하지 않는다.
**하나의 기능을 백엔드 API + 프론트 화면까지 한 번에** 끝내며, 그 사이클을 반복한다. 그래야 매번 "동작하는 것"을 보며 배운다.

권장 순서 (기획서 MVP 기준):

1. **TODO CRUD** ← 가장 단순. 여기서 백엔드 골격(도메인→리포지토리→서비스→컨트롤러)을 익히고, **JdbcTemplate으로 먼저 구현 → JPA로 변환**하며 영속성을 바닥부터 배운다 (4-3 참고)
2. BLOCK_GROUP + BLOCKED_APP (앱 등록)
3. TODO ↔ BLOCK_GROUP 연결 (다대다)
4. FOCUS_SESSION (포모도로 세션 기록)
5. DISTRACTION_EVENT (흐트러짐 기록)
6. 통계 집계 API + 대시보드
7. 계정/로그인

앞 슬라이스에서 배운 패턴이 다음 슬라이스에서 그대로 반복된다 → 2번부터는 점점 혼자 빨라진다.

---

## 2. 한 슬라이스의 진행 사이클

각 기능은 항상 이 순서로 돈다:

```
① 에이전트: 요구사항 정리 (프론트+백 공통 계약 = API 스펙)
        ▼
② 백엔드: 에이전트가 가이드 문서 작성 → 내가 구현 → 에이전트가 리뷰
        ▼
③ 프론트: 에이전트가 초안 구현 → 내가 리팩토링
        ▼
④ 통합 확인: dev 서버 + 백엔드 띄우고 실제 동작 확인
```

②와 ③은 API 스펙(①)만 합의되면 병렬로 가도 된다. axios 레이어는 이미 `frontend/src/renderer/src/lib/api.ts`에 있고, 백엔드 CORS도 `WebConfig.kt`에 열려 있다.

---

## 3. 프론트엔드 협업 규칙 (에이전트 초안 → 내가 리팩토링)

### 에이전트가 줄 것

- **동작하는 초안.** 타입 에러/린트 없이 `pnpm dev`에서 도는 상태까지.
- 기존 스택·컨벤션 준수: TanStack Query + axios, shadcn/ui, Tailwind, `@/` 경로 별칭, 함수형 컴포넌트 + 명시적 반환 타입 (`App.tsx` 스타일 그대로).
- **리팩토링 포인트를 코드에 남긴다.** 내가 손댈 지점을 명시:
  ```tsx
  // REFACTOR(jiho): 이 로직 커스텀 훅(useTodos)으로 분리 검토
  // WHY: 컴포넌트가 데이터 페칭 + 렌더 둘 다 하고 있음
  ```
- PR/메시지 말미에 **"초안 결정 노트"** 3~5줄: 왜 이 구조로 했는지, 어디를 내가 바꾸면 좋은지, 대안은 무엇이었는지.

### 에이전트가 하지 말 것

- 과하게 추상화한 "완벽한" 구조 (내가 리팩토링으로 배울 여지를 남길 것)
- 한 번에 여러 기능 뭉치기 → 항상 슬라이스 하나 단위

### 내가 할 것

- 초안을 읽고 **직접 리팩토링**하며 이해. 이해 안 되는 부분은 "왜 이렇게 했어?" 질문.
- 리팩토링 후 에이전트에게 **역리뷰** 요청 가능: "내가 이렇게 바꿨는데 더 나은 방법 있어?"

## 4. 백엔드 협업 규칙 (에이전트 가이드 → 내가 구현)

**에이전트는 백엔드 프로덕션 코드(`src/main/kotlin/app/**`)를 작성하지 않는다.**
대신 슬라이스마다 아래 형식의 **가이드 문서**를 `.context/backend-guides/<슬라이스>.md`에 만들어 준다.

### 4-1. 가이드 문서 형식 (에이전트가 채움)

```markdown
# [슬라이스명] 백엔드 가이드

## A. 무엇을 만드나 (요구사항)
- 이 기능이 하는 일 1~2줄
- 관련 기획서 섹션 링크

## B. API 계약 (프론트와 공유되는 유일한 진실)
| 메서드 | 경로              | 요청 본문        | 응답            | 상태코드 |
| ------ | ----------------- | ---------------- | --------------- | -------- |
| GET    | /api/todos        | -                | Todo[]          | 200      |
| POST   | /api/todos        | CreateTodoReq    | Todo            | 201      |
| ...    |                   |                  |                 |          |
- 각 DTO 필드와 검증 규칙(@NotBlank 등) 표로 명시

## C. 도메인 모델
- 엔티티 필드 목록과 타입, 관계 (기획서 7장 데이터 모델 기준)
- DB 없이 시작할지(인메모리) / JPA+H2로 갈지 명시

## D. 구현 체크리스트 (내가 채울 빈칸)
- [ ] domain/Todo.kt — 필드 X, Y, Z
- [ ] dto/TodoDtos.kt — 요청/응답 DTO
- [ ] repository/TodoRepository.kt
- [ ] service/TodoService.kt — 비즈니스 규칙: ...
- [ ] controller/TodoController.kt — B의 계약대로
- [ ] test/... — 최소 컨트롤러 테스트 1개

## E. 배워야 할 개념 (막히기 전에 읽을 것)
- 개념 이름 + 한 줄 설명 + 공식 문서 링크
- 예: "@RestController vs @Controller", "생성자 주입", "@Valid"

## F. 힌트 사다리 (막혔을 때만 순서대로 펼침)
1. 방향만: "Service가 Repository를 어떻게 받을지 생각해봐 (주입)"
2. 구조: 시그니처만 — `fun create(req: CreateTodoReq): Todo`
3. 의사코드: 한글 주석 단계
4. (정답 코드는 여기 두지 않는다 — 요청 시 별도로)
```

### 4-2. 막혔을 때 규칙 (중요)

내가 백엔드에서 막히면, 에이전트는 **바로 완성 코드를 주지 않는다.** F의 **힌트 사다리를 1→2→3 순서로** 한 단계씩 올린다.
- 나는 "다음 힌트" 또는 "정답 보여줘"로 단계를 조절한다.
- 에러가 나면: 에이전트는 **에러 메시지 읽는 법 + 원인 후보**를 먼저 알려주고, 내가 못 풀면 그때 고칠 위치를 짚어준다.
- 내가 짠 코드는 **리뷰**해준다: 동작하는가 + 왜 이게 관용적인가(Kotlin/Spring 컨벤션) + 놓친 엣지케이스.

### 4-3. 백엔드 영속성 학습 경로 (JdbcTemplate → JPA)

지금 `build.gradle.kts`에는 web + validation만 있고 DB가 없다. 슬라이스 1(TODO CRUD)은 **같은 기능을 두 번 구현**하며 영속성을 아래→위 순서로 배운다:

**1단계 — JdbcTemplate (SQL을 내 손으로)**
- 의존성: `spring-boot-starter-jdbc` + H2. `schema.sql`로 테이블 직접 정의.
- Repository를 `JdbcTemplate` / `NamedParameterJdbcTemplate`으로 작성 → INSERT/SELECT/UPDATE/DELETE SQL을 직접 쓰고, `RowMapper`로 결과를 엔티티에 매핑.
- 배우는 것: 테이블·컬럼·PK, SQL, 커넥션/트랜잭션 경계(`@Transactional`), ResultSet 매핑을 **명시적으로** 다뤄본다. "DB가 실제로 뭘 하는지"의 바닥을 본다.

**2단계 — JPA로 변환 (같은 기능, 추상화 위로)**
- 컨트롤러·서비스·API 계약은 **그대로 두고 Repository 계층만 교체**한다 (인터페이스가 왜 유용한지 여기서 체감).
- 의존성: `spring-boot-starter-data-jpa`. `@Entity`/`@Id`/관계 애너테이션, `JpaRepository` 도입.
- 배우는 것: 1단계에서 손으로 쓰던 SQL을 JPA가 어떻게 대신 생성하는지, 그 대가로 무엇을(영속성 컨텍스트·더티체킹·N+1) 새로 알아야 하는지. **직접 써봤기 때문에** JPA의 편의와 함정이 둘 다 선명하게 보인다.

> 이 "두 번 구현"은 낭비가 아니라 슬라이스 1의 핵심 학습 목표다. 슬라이스 2부터는 JPA로만 간다.

## 5. 공통 규칙

### 브랜치 / 커밋
- 슬라이스 단위 브랜치: `feat/todo-crud` 등.
- 커밋 메시지 규칙은 기존 히스토리 따름: `feat(BE):`, `feat(FE):`, `docs:`.
- 프론트 초안과 백엔드 구현은 커밋을 분리 (누가 무엇을 했는지 학습 기록으로 남김).

### "완료" 기준 (슬라이스별)
1. 백엔드 `./gradlew test` 통과 + 해당 API `curl`로 응답 확인
2. 프론트 `pnpm typecheck` + `pnpm lint` 통과
3. 백엔드·프론트 둘 다 띄운 상태에서 화면에서 기능이 실제로 동작
4. 내가 그 슬라이스의 흐름을 **말로 설명할 수 있음** ← 학습 목표 달성 기준

### 확인 명령
```bash
# 백엔드
cd backend && ./gradlew bootRun         # 서버 (8080)
cd backend && ./gradlew test            # 테스트

# 프론트
cd frontend && pnpm dev                 # 앱
cd frontend && pnpm typecheck && pnpm lint
```

## 6. 매 작업 시작 시 에이전트에게 하는 말 (템플릿)

- 프론트: **"[기능] 프론트 초안 만들어줘. 리팩토링 포인트 남기고 결정 노트 붙여줘."**
- 백엔드: **"[기능] 백엔드 가이드 써줘. 코드는 내가 짤 거야. 힌트 사다리까지."**
- 막혔을 때: **"[기능] [파일]에서 막혔어. 다음 힌트 하나만."**
- 리뷰: **"내가 짠 [파일] 리뷰해줘. 관용적인지랑 놓친 부분."**
